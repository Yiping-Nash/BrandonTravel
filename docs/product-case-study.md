# 产品复盘：从聊天到共享旅行状态

## 问题与产品判断

旅行计划不是一段聊天文本。人会改日期、拖动活动，AI 也会提出调整；如果各自维护一份计划，就难以知道最终安排是什么。产品选择时间表为核心，把编辑与检查做成共享能力，AI 作为消费者。

用户负责产品场景、范围、领域含义与授权边界；Codex 负责边界内的实现与实验。项目由一位产品负责人借助 AI coding 推进，没有传统多人团队或企业规模落地的证据。

## 三个可展示行为

1. 缩短行程：越界活动保留身份和内容，回待安排并按原日期分组。
2. 查看问题：重叠由时间计算得出；缺路线／营业资料时明确不知道，不用模型猜。
3. 共同编辑：Agent 读取最新状态、提出差异；确认前状态不变，确认后事务提交并读回。

## 一个有价值的失败

Sprint B 插入活动出现过时间换算错误、反复尝试不可行时段和未经授权缩短其他活动。改进是共享规划服务提供引擎验证的候选，而非让 Agent 宿主重写计算或降低 Grader。最后重复回归通过，但并不证明模型独立处理所有时间推理。

## 求职表述边界

可以说：设计并落地共享领域能力、受控 Agent 写入和固定场景评测闭环。不能说：独立泛化验证已完成、SDK 已替换生产 Agent、企业 ROI 已实测、所有失败已消除。

24 个泛化案例与少量独立验证案例是后续实验方向，当前未取得完整冻结集评测证据。SDK Spike 的 23/24 是使用预算，不是通过率；51 行只指 MCP 适配器，试验驱动约 700 行。
